### 问题 3：图片数据持久化 ℹ️ 需要确认

**当前状态**：
图片数据已经通过 Zustand 的 persist 中间件持久化，包括：
- `phononImages`：全局声子谱图片列表
- `currentSessionPhononImages`：当前会话的声子谱图片
- 存储位置：localStorage（key: `researchmind-storage`）

**已实现的持久化**：
1. **数据结构**（`ui/src/store/useAppStore.ts`）：
   ```typescript
   export interface PhononImage {
     name: string
     path?: string
     url?: string
     filename?: string
     type: string
     description?: string
     base64?: string  // Base64 编码的图片数据
     timestamp?: string | number
     dispersionCsvPath?: string
     dosCsvPath?: string
   }
   ```

2. **持久化配置**（`ui/src/utils/storage.ts` 第 156-173 行）：
   - 会话数据（sessions）
   - 当前会话结构（currentSessionStructures）
   - 当前会话文件（currentSessionFiles）
   - 声子谱图片（phononImages, currentSessionPhononImages）

3. **图片加载逻辑**（`ui/src/components/PhononVisualization.tsx` 第 136-146 行）：
   ```typescript
   const getImageUrl = (image: PhononImage): string => {
     if (image.base64) return `data:image/png;base64,${image.base64}`
     if (image.url) return resolveFileUrl(image.url)
     if (image.filename) return resolveFileUrl(`/images/phonon/${image.filename}`)
     if (image.path) return resolveFileUrl(`/images/${image.path}`)
     return ''
   }
   ```

**潜在问题**：
1. **base64 数据未生成**：
   - 后端返回的图片数据通常只包含 `url` 和 `path`
   - 没有生成 base64 编码的图片数据
   - 刷新页面后，如果文件路径变化，图片可能加载失败

2. **session_id 依赖**：
   - 图片 URL 包含 session_id：`/api/images/phonon/{session_id}/phonon_results/file.png`
   - 如果 session_id 变化，URL 会失效

**建议的改进方案**：

#### 方案 A：后端生成 base64（推荐）
在后端生成图片时，同时生成 base64 编码：

```python
# services/image_handler.py
def _create_phonon_image(path: str, ...):
    # 读取图片文件并转换为 base64
    if os.path.exists(path):
        with open(path, 'rb') as f:
            image_data = f.read()
            base64_data = base64.b64encode(image_data).decode('utf-8')
    
    return {
        "name": name,
        "url": url,
        "base64": base64_data,  # 添加 base64 数据
        ...
    }
```

优点：
- ✅ 图片数据完全独立于文件系统
- ✅ 刷新页面后仍然可以显示
- ✅ 不依赖 session_id

缺点：
- ❌ localStorage 空间占用较大
- ❌ 可能超出 localStorage 配额（5-10MB）

#### 方案 B：前端按需加载并缓存
前端在首次加载图片时，将其转换为 base64 并保存：

```typescript
// 在图片加载成功后
const handleImageLoad = async (image: PhononImage) => {
  if (!image.base64 && image.url) {
    const response = await fetch(resolveFileUrl(image.url))
    const blob = await response.blob()
    const reader = new FileReader()
    reader.onloadend = () => {
      const base64 = reader.result as string
      // 更新 store 中的图片数据
      updatePhononImage(image.name, { base64 })
    }
    reader.readAsDataURL(blob)
  }
}
```

优点：
- ✅ 按需加载，不浪费空间
- ✅ 用户查看过的图片会被缓存

缺点：
- ❌ 首次加载需要网络请求
- ❌ 实现较复杂

#### 方案 C：使用 IndexedDB（最佳方案）
使用 IndexedDB 存储图片数据，突破 localStorage 的大小限制：

```typescript
// 使用 idb-keyval 库
import { set, get } from 'idb-keyval'

// 保存图片
await set(`phonon_image_${image.name}`, base64Data)

// 读取图片
const base64Data = await get(`phonon_image_${image.name}`)
```

优点：
- ✅ 存储空间大（通常 50MB+）
- ✅ 异步操作，不阻塞 UI
- ✅ 支持二进制数据

缺点：
- ❌ 需要引入新的依赖
- ❌ API 相对复杂

**需要用户确认**：
1. 具体是指哪些图片数据需要持久化？
   - [ ] 声子谱图片（phonon dispersion, DOS）
   - [ ] 结构图（crystal structures）
   - [ ] 用户上传的图片
   - [ ] 其他可视化图表

2. 持久化的目的是什么？
   - [ ] 页面刷新后保留
   - [ ] 跨会话访问
   - [ ] 离线查看

3. 可接受的存储方案？
   - [ ] 方案 A：后端生成 base64（简单但占空间）
   - [ ] 方案 B：前端按需缓存（平衡方案）
   - [ ] 方案 C：使用 IndexedDB（最佳但复杂）
